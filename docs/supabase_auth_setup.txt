OMECOnnect Customer Supabase Setup

The customer starter now uses Supabase Auth and PostgREST when configured. Until credentials are supplied, real mode stays enabled and reports that Supabase is not configured; it does not silently use demo data.

1. Create a Supabase project and open Project Settings > API.

2. In customer-mobile-app/config.js set:

window.OMECO_CONFIG = {
  demoMode: false,
  supabaseUrl: 'https://YOUR_PROJECT_REF.supabase.co',
  supabaseAnonKey: 'YOUR_PUBLISHABLE_OR_ANON_KEY',
  appName: 'OMECOnnect'
};

Use the project URL and the publishable (or legacy anon) key only. Never place the service_role/secret key in a browser, mobile app, or source control. The public key is safe to ship only with the RLS migration below applied.

3. In the Supabase SQL Editor, run these scripts in order:
- database/supabase_schema.sql
- database/phase2_supabase_auth_and_access.sql

The migration:
- Creates a public profile row for new Supabase Auth users
- Keeps customer account numbers pending until OMECO staff verifies them
- Uses admin_accounts membership for administrator authorization; public.users.role is not trusted as an admin role
- Restricts customer queries with Row Level Security
- Makes announcements visible only when published and global or relevant to the customer's verified service area
- Creates notifications for newly published announcements and newly created bills
- Provides a scheduled function for due-date reminders

4. Configure Supabase Auth:
- Enable email/password sign-in
- Configure email confirmation and redirect URLs for your deployed app
- Set the password minimum and email rate limits in the Auth settings

5. Promote a trusted admin account only after that person has registered and verified their email. In SQL Editor, replace the email and employee details:

INSERT INTO public.admin_accounts (user_id, employee_id, department)
SELECT id, 'EMPLOYEE-ID', 'IT'
FROM auth.users
WHERE email = 'admin@your-organization.example'
ON CONFLICT DO NOTHING;

Administrator access is based on this protected membership table, not a user-editable profile field. Do not let customer clients insert or update admin_accounts.

6. Account-number verification:
- A customer signs up and authenticates with Supabase Auth.
- The app submits the entered OMECO account number to account_verification_requests.
- OMECO staff must compare it with authorized OMECO records.
- Only staff should link a verified official customer_accounts row to the user's auth ID and set verification_status to 'verified'.
- Until then, the customer cannot read account-specific bills, meter readings, or service-area announcements.
- Never use the account number by itself to disclose bill information.

7. Due-date reminder scheduling:
The migration provides public.queue_due_bill_notifications(), which queues one reminder per bill within three days of its due date. Enable pg_cron under Database > Extensions if available, then schedule the function to run daily. Supabase cron schedules use UTC; 00:00 UTC is 08:00 in the Philippines:

SELECT cron.schedule(
  'omeco-due-bill-notifications',
  '0 0 * * *',
  $$ SELECT public.queue_due_bill_notifications(); $$
);

If pg_cron is unavailable on your plan, run this function from a trusted scheduled server/Edge Function using a server-side credential. Never expose a service-role key to the app.

8. Run the local customer screen:
- Serve the workspace over HTTP(S), then open customer-mobile-app/index.html.
- The current customer-mobile-app/config.js is set to demoMode: true for local testing.
- Demo login: demo.customer@omeco.test / DemoCustomer123!
- Demo records are fabricated and must never be treated as official OMECO information.
- Before connecting to Supabase, set demoMode to false and enter the project's URL and public key.

Production notes:
- The current browser prototype keeps access tokens in memory only, so users sign in again after a page reload. A native mobile implementation should use Supabase's supported client SDK and OS secure storage.
- Verify email confirmation, RLS, account approval, and role permissions in a non-production Supabase project before using any real consumer data.
- The chat responses are a limited rule-based demonstration, not a deployed generative AI service.
